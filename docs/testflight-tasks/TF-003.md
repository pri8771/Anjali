# TF-003 — Publish Privacy URL and Set Beta Contacts

**Status:** blocked  
**Owner:** product/privacy owner, release owner, public-site owner  
**Depends on:** approved public host and real contact owners  
**Blocks:** final TF-004 packet and external beta  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-003-public-contacts.md`
**Prepared input:** policy/metadata source audit at
`quality/evidence/2026-07-29-tf-003-tf-004-metadata-preflight.md`

## Task description

**Summary:** Publish accurate privacy information and establish reachable beta
feedback/support contacts.

**Expected change:** As a tester or Apple reviewer, I want to understand the app's
privacy behavior and reach a real person without creating an account.

**What and why:** Repository policy text exists, but its public URLs and beta
contact are placeholders. External TestFlight requires a Feedback Email; the
privacy URL must be public and must agree with the binary. The support URL is a
later App Store requirement and should be operational before public launch.

**How:** Human owners approve policy/contact values; an implementer publishes
them to a stable HTTPS host, verifies access from signed-out desktop/mobile
contexts, synchronizes repository placeholders, and records evidence.

## Subtasks

### TF-003.1 — Reconcile policy text with the release scope

**Description:** Summary: prove the policy describes the candidate. Expected change:
as a privacy-conscious user, I need claims that match actual behavior. What/why:
stale “no data collected” language becomes misleading if code or SDK behavior
changes. How: compare policy and terms with architecture, Info.plist, privacy
manifest, dependencies, and current v1 scope.

**Procedure:**

1. Review `AppStore/privacy_policy.md` and `terms_of_service.md`.
2. Confirm the app has no network layer, account, analytics, ads, IAP,
   third-party SDK, or collected/transmitted user data.
3. Confirm SwiftData/UserDefaults/local notifications are accurately described.
4. Confirm contact and effective-date language is approved.
5. Route any legal wording change to the privacy/legal owner.

**Done when:** Privacy/product owners approve policy text against the exact
shipping behavior.

**Evidence:** Approval owner/date and behavior-to-policy checklist.

**Stop/escalate:** Any networking/SDK/data mismatch requires code/privacy
reassessment before publication.

### TF-003.2 — Publish and verify the privacy policy

**Description:** Summary: place the approved policy at a stable public URL. Expected change:
as a tester, I can read the policy without login or special software.
What/why: a repository file is not a public policy URL. How: the site owner
publishes the exact approved text over HTTPS and an implementer tests it from
outside an authenticated session.

**Procedure:**

1. Product owner selects an approved domain/path.
2. Publish the approved policy without adding unapproved trackers/cookies.
3. Open it in a signed-out browser and on a mobile device.
4. Confirm valid HTTPS, readable layout, correct app name/date/contact, and no
   redirect to login.
5. Record the canonical URL; do not use a temporary preview URL.

**Done when:** Stable public HTTPS policy is readable in both verification
contexts and matches the repository text.

**Evidence:** URL, publish/verify dates, verifier, HTTP/result summary, redacted
screenshot reference.

**Stop/escalate:** Stop on TLS error, authentication, geoblock, tracking
mismatch, stale text, or inaccessible mobile layout.

### TF-003.3 — Establish and test the beta feedback mailbox

**Description:** Summary: provide the required monitored TestFlight contact.
Expected change: as a tester, I can report a problem and receive a response. What/why:
an unmonitored or fabricated address fails both Apple and users. How: an owner
creates/selects the mailbox, defines coverage, sends a test from an unrelated
account, and verifies reply delivery.

**Procedure:**

1. Choose an organizational address suitable for beta feedback.
2. Assign a primary owner and backup.
3. Define expected review cadence and escalation for privacy/content/P0 reports.
4. Send a test from outside the organization.
5. Reply and confirm both directions arrive without spam rejection.
6. Record only the public address, not private mailbox configuration.

**Done when:** The mailbox receives/replies and named owners accept coverage.

**Evidence:** Public email, owner roles, test date/result, response cadence.

**Stop/escalate:** Do not use a personal/unapproved or unmonitored address.

### TF-003.4 — Publish or schedule the support URL

**Description:** Summary: create a durable support destination for App Store
submission and users. Expected change: as a user, I can find help after the beta.
What/why: Feedback Email serves TestFlight, but the storefront later requires a
support URL. How: publish a minimal accurate support page or record an owner and
deadline if it is explicitly deferred.

**Procedure:**

1. Decide support-page scope: app name, current version support, feedback
   email, privacy link, basic troubleshooting.
2. Publish on stable HTTPS without unapproved tracking, or record an AS-003
   owner/date if deferred.
3. Test signed-out desktop/mobile access.
4. Do not claim live chat, SLA, or features that do not exist.

**Done when:** A verified support URL exists, or an explicit App Store
follow-on owner/date is approved and does not masquerade as complete.

**Evidence:** URL/result or deferral decision.

**Stop/escalate:** External beta may proceed only according to the product
owner's documented gate; App Store submission cannot proceed without the live
URL.

### TF-003.5 — Verify privacy/contact behavior externally

**Description:** Summary: independently exercise all public contact paths. Expected change:
as release owner, I need proof that values work outside the creator's
session. What/why: cached/authenticated access can hide broken public
configuration. How: a second verifier tests URLs/mailbox and compares content
to the repo.

**Procedure:**

1. Use a signed-out browser/network not relying on site-owner authentication.
2. Verify privacy URL and support URL when available.
3. Compare page text/version/date to repository files.
4. Repeat feedback-email send/reply test.
5. Check mobile legibility and accessible link labels.
6. Record failures before any metadata synchronization.

**Done when:** Independent verification passes every available public value.

**Evidence:** Verifier/date/device/browser/result matrix.

**Stop/escalate:** Any failure returns to the responsible publishing/mailbox
subtask.

### TF-003.6 — Synchronize repository values and commit evidence

**Description:** Summary: replace placeholders with approved public values.
Expected change: as the next implementer, I need repository metadata to be the
canonical copy. What/why: App Store Connect-only values would drift. How: update
repository URL/contact fields, search for stale placeholders, review the diff,
and commit evidence without private data.

**Procedure:**

1. Update `AppStore/README.md`, `AppStore/testflight_metadata.md`, policy/terms
   contact text, and other canonical references as applicable.
2. Run:

```bash
rg -n 'TBD|PUBLIC_PRIVACY|MONITORED_BETA|PUBLIC_SUPPORT' AppStore docs
```

3. Classify every remaining match as resolved or explicitly deferred.
4. Create the TF-003 evidence file.
5. Review diff for accidental policy changes or private information.
6. Update TF-003 status.

**Done when:** Approved values are consistent across repo files and evidence
proves external verification; no unexplained placeholder remains.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-003-public-contacts.md`.

**Stop/escalate:** Never commit private review phone/contact information merely
to eliminate a placeholder.
