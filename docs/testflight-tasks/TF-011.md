# TF-011 — Submit and Clear External Beta App Review

**Status:** blocked  
**Owner:** authorized App Manager/Admin/TestFlight operator  
**Depends on:** TF-001, TF-003, TF-004, TF-010  
**Blocks:** TF-012  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-011-beta-review.md`

## Task description

**Summary:** Configure a closed external group, submit the approved build and
truthful metadata to Apple, respond to review, and record approval.

**Expected change:** As an invited practitioner, I want Apple and the release team to
have reviewed the beta before it is distributed beyond internal users.

**What and why:** External testers are not App Store Connect users and the first
external build generally undergoes Beta App Review. Submitting incomplete or
drifted metadata increases rejection risk.

**How:** Run a dependency preflight, create an email-invite external group,
attach exact build/What to Test/Test Information, submit once, monitor/respond
accurately, and record approval/expiration before invitations.

## Subtasks

### TF-011.1 — Run the external-readiness preflight

**Description:** Summary: verify every prerequisite still applies to the same
build. Expected change: as product owner, I do not expose unreviewed sacred content
or an unapproved binary. What/why: earlier task completion can be invalidated by
source/metadata changes. How: compare evidence SHAs/builds/statuses and public
values immediately before external configuration.

**Procedure:**

1. Confirm TF-001 22/22 sign-off applies to candidate content SHA.
2. Confirm public privacy URL and feedback mailbox still work.
3. Confirm TF-004 packet SHA/approvals and no placeholders.
4. Confirm TF-010 GO identifies the exact TF-009 build.
5. Confirm no new P0/P1/content/privacy issue.
6. Record preflight verifier/date.

**Done when:** All dependencies are current and point to one build.

**Evidence:** Dependency/build comparison table.

**Stop/escalate:** Any stale/mismatched dependency blocks external group setup.

### TF-011.2 — Create the controlled external group

**Description:** Summary: create the container for invited non-team testers.
Expected change: as release owner, I can limit the first external cohort and revoke
access if needed. What/why: a public link is unnecessary risk before controlled
feedback. How: create a clearly named external group with email invitation
distribution and no public link.

**Procedure:**

1. Create group such as `Anjali 1.0 Closed Beta`.
2. Set owner/purpose/cohort ceiling consistent with TF-012.
3. Leave public link disabled.
4. Do not add/invite testers yet.
5. Record group name and access method.

**Done when:** Closed external group exists with no unintended tester access.

**Evidence:** Group name/type/owner/date.

**Stop/escalate:** Accidental public-link enablement must be disabled and
recorded.

### TF-011.3 — Attach build and approved information

**Description:** Summary: configure exactly what Apple and future testers
receive. Expected change: as reviewer/tester, I see the approved description,
contacts, notes, and test instructions. What/why: wrong build or drifted fields
invalidates review. How: add TF-010 build, paste canonical What to Test, verify
global Test Information, and compare saved values.

**Procedure:**

1. Select exact version/build from TF-010 evidence.
2. Add to external group.
3. Paste build-specific What to Test from TF-004.
4. Verify Beta Description, Feedback Email, Review Contact, sign-in state,
   Review Notes, and privacy URL.
5. Reopen and second-person compare with repository packet.
6. Confirm invitations remain off pending review.

**Done when:** Group/build/metadata exactly match approved repo values.

**Evidence:** Redacted field/build comparison.

**Stop/escalate:** Any discrepancy is resolved in repo first.

### TF-011.4 — Submit for Beta App Review

**Description:** Summary: send one complete build submission to Apple. Expected change:
as external tester, the build receives Apple's beta review gate.
What/why: repeated uninformed submissions consume limits and obscure root
causes. How: authorized operator reviews summary, submits once, and records
submission identifiers/time/status.

**Procedure:**

1. Confirm no other build for version is already in Beta App Review.
2. Review all fields and build one final time.
3. Submit for Beta App Review.
4. Record submission time, operator, build, group, initial status.
5. Do not promise review duration.
6. Do not resubmit after rejection without diagnosis; Apple limits submissions
   over a 24-hour period.

**Done when:** Exact build enters Beta App Review with recorded status.

**Evidence:** Submission/status record.

**Stop/escalate:** UI/account validation error must be preserved and resolved,
not bypassed.

### TF-011.5 — Monitor and respond to App Review

**Description:** Summary: manage questions/rejection without diverging from
truth or repo. Expected change: as Apple reviewer, I receive timely, accurate answers.
What/why: unrecorded ad hoc responses can contradict product/privacy. How:
monitor status/messages, copy exact issues to restricted evidence, route by
owner, draft from repository facts, approve, respond, and rerun affected gates.

**Procedure:**

1. Check App Store Connect messages/status at agreed cadence.
2. Preserve exact question/rejection and timestamp.
3. Classify content, metadata, binary, compliance, or access issue.
4. Draft response using repo evidence; responsible owner approves.
5. Metadata change updates TF-004 and syncs copies.
6. Binary change returns to TF-005/new build and required reruns.
7. Record response and next status.

**Done when:** No unresolved review message remains.

**Evidence:** Redacted message/response/status timeline.

**Stop/escalate:** Never claim behavior/evidence not present to secure approval.

### TF-011.6 — Record approval and release handoff

**Description:** Summary: prove the build is approved but not yet broadly
invited. Expected change: as TF-012 owner, I know which build/group can be safely
used and when it expires. What/why: approval does not define cohort/triage
readiness by itself. How: record approval status/date, build expiration, group,
metadata SHA, and invitation hold.

**Procedure:**

1. Confirm Beta App Review status is approved.
2. Record version/build, group, approval date, and 90-day expiration shown by
   Apple.
3. Confirm feedback email/public privacy URL again.
4. Keep invitations withheld until TF-012.1 cohort approval.
5. Complete evidence and update backlog.

**Done when:** Approved build/group has an unambiguous, dated handoff to TF-012.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-011-beta-review.md`.

**Stop/escalate:** Expired, superseded, or unresolved-review build cannot hand
off.
