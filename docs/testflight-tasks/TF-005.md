# TF-005 — Freeze the Release Candidate and Unique Build Identity

**Status:** blocked  
**Owner:** engineering/release owner  
**Depends on:** TF-001, TF-002, approved text-only scope  
**Blocks:** final TF-004 build binding and TF-006 through TF-010  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-005-release-candidate.md`

## Task description

**Summary:** Convert reviewed source into one immutable, uniquely numbered
release candidate.

**Expected change:** As QA and release operators, we want every test, archive, and
upload to refer to one exact source commit and build number so results cannot be
mistakenly transferred between binaries.

**What and why:** Local build `1` is not proof that build `1` is unused in App
Store Connect, and a dirty working tree is not a reproducible candidate. Content
must be approved before freeze because later corrections invalidate the build.

**How:** Verify dependencies, reconcile scope, query Apple's build history,
select/update a unique build number, confirm bundle inputs, create a clean
candidate commit, and publish an immutable identity record.

## Subtasks

### TF-005.1 — Verify dependencies and freeze scope

**Description:** Summary: establish exactly what the candidate includes. Expected change:
as QA, I need a stable feature/content boundary before testing. What/why:
freezing before human content and Apple identity decisions invites rework.
How: read TF-001/TF-002 evidence, compare product docs/contracts, and obtain
product approval of the text-only beta scope.

**Procedure:**

1. Confirm TF-001 evidence passes 22/22 at a recorded content SHA.
2. Confirm TF-002 evidence identifies team, bundle, app record, and owner.
3. Confirm scope: iOS 17+, iPhone/iPad, offline/accountless, text-only prayers,
   optional local reminders, no IAP/network/analytics/third-party SDK.
4. List every intentionally deferred feature, especially reviewed audio.
5. Obtain product, content, engineering, and release owner approval.

**Done when:** Dependencies are evidenced and a named owner approves one
unambiguous candidate scope.

**Evidence:** Dependency links, included/excluded scope, approvers/dates.

**Stop/escalate:** Any unresolved content, identity, or scope decision blocks
freeze.

### TF-005.2 — Reconcile the release working tree

**Description:** Summary: ensure the candidate contains only understood changes.
Expected change: as a maintainer, I want to know exactly what will ship without
destroying another person's work. What/why: the repository may be dirty; blind
cleanup can lose user changes, while bundling unrelated edits creates an
unreviewable binary. How: inspect status/diff, classify every change, and move
only approved scope into the candidate branch/commit.

**Procedure:**

1. Run `git status --short` and `git diff --stat`.
2. Classify each path as candidate, unrelated preserved work, generated
   evidence, or accidental.
3. Do not reset, checkout, delete, or stage unrelated user work.
4. If isolation needs a branch/worktree, use a `codex/` branch and preserve the
   original tree.
5. Require a clean candidate checkout before later validation.

**Done when:** Every candidate change is intentional/reviewed and the candidate
checkout has no unexplained modification.

**Evidence:** Classified path list, branch, base SHA, reviewer.

**Stop/escalate:** Overlapping unreviewed edits require their owner; do not
guess which version to keep.

### TF-005.3 — Determine the next unique build number

**Description:** Summary: select a build string Apple has not successfully
processed for version 1.0. Expected change: as the upload operator, I want the first
upload to be accepted and traceable. What/why: repository history alone cannot
show App Store Connect uploads. How: authorized operator inspects build history,
reports the highest successful/processing build, and release owner chooses a
higher integer.

**Procedure:**

1. Open App Store Connect → Anjali → TestFlight/build history.
2. Filter/inspect marketing version `1.0`.
3. Record every completed or processing build number relevant to uniqueness.
4. Select a monotonically higher positive integer.
5. Have a second authorized person verify it is unused immediately before
   source update.

**Done when:** Chosen build is documented as unused and higher than prior
successful/processing 1.0 uploads.

**Evidence:** Redacted history summary, chosen build, operator/verifier/date.

**Stop/escalate:** Never infer uniqueness from `CURRENT_PROJECT_VERSION = 1`.

### TF-005.4 — Update and verify version/build settings

**Description:** Summary: write the approved identity to both app build
configurations. Expected change: as a tester, the installed version/build should
match evidence. What/why: mismatched Debug/Release settings can make local tests
and uploaded archive disagree. How: edit only app-target Debug and Release
`CURRENT_PROJECT_VERSION`, preserve approved marketing/bundle values, and
inspect resolved build settings.

**Procedure:**

1. Use `apply_patch` to update both app-target build-number occurrences in
   `Anjali/Anjali.xcodeproj/project.pbxproj`.
2. Keep `MARKETING_VERSION = 1.0` unless product explicitly approved another
   version.
3. Keep `PRODUCT_BUNDLE_IDENTIFIER = app.anjali.Anjali`.
4. Run:

```bash
xcodebuild -showBuildSettings \
  -project Anjali/Anjali.xcodeproj \
  -scheme Anjali \
  -configuration Release |
  rg 'PRODUCT_BUNDLE_IDENTIFIER|MARKETING_VERSION|CURRENT_PROJECT_VERSION|DEVELOPMENT_TEAM'
```

5. Compare resolved values to TF-002/TF-005 decisions.

**Done when:** Resolved Release settings exactly match approved team, bundle,
version, and build; project diff changes only intended settings.

**Evidence:** Project diff and resolved settings with no secrets.

**Stop/escalate:** Any unexpected inherited override or signing identity blocks
freeze.

### TF-005.5 — Confirm release-bundle inputs and privacy boundary

**Description:** Summary: ensure candidate inputs still satisfy text-only,
offline, Data-Not-Collected scope. Expected change: as a tester, I should not receive
provisional audio or undisclosed behavior. What/why: a release freeze is the
last source-level opportunity to catch target-membership/config drift. How:
validate catalog flags, search audio/network/dependency surfaces, and verify
privacy/export declarations.

**Procedure:**

1. Run both content validators.
2. Confirm all `audioAssetName` values are null.
3. Inspect Xcode membership exceptions and ensure provisional audio is excluded.
4. Confirm `PrivacyInfo.xcprivacy` exists and Info.plist retains
   `ITSAppUsesNonExemptEncryption = NO`.
5. Check dependency manifests/project for new third-party packages.
6. Search changed app source for newly introduced networking/analytics/account
   behavior and reconcile documentation if any exists.

**Done when:** Candidate source still matches offline/text-only/privacy scope.

**Evidence:** Commands/results and reviewed membership/privacy diff.

**Stop/escalate:** Any unexpected audio, SDK, networking, or data behavior
requires product/privacy review and likely returns to earlier tasks.

### TF-005.6 — Create the immutable candidate commit

**Description:** Summary: create the SHA used by every later gate. Expected change:
as release stakeholders, we can refer to one binary source identity. What/why:
testing “the latest branch” is not reproducible. How: stage only approved paths,
review staged diff, commit intentionally, and record the full SHA.

**Procedure:**

1. Run final `git diff --check`.
2. Stage only approved candidate files.
3. Review `git diff --cached --stat` and the complete staged diff.
4. Commit with version/build and release-candidate intent.
5. Record `git rev-parse HEAD`.
6. Require `git status --short` to be empty in the candidate checkout.
7. Do not amend after TF-006 begins; any source change creates a new candidate
   and usually a new build number.

**Done when:** A clean, immutable Git SHA contains exactly the approved
candidate.

**Evidence:** Commit SHA, branch, parent SHA, staged path list, approver.

**Stop/escalate:** Unexplained diff or dirty candidate means no freeze.

### TF-005.7 — Publish identity evidence and lock change control

**Description:** Summary: distribute the source/version/build tuple and rules
for invalidation. Expected change: as every downstream operator, I can confirm I am
testing/archiving the approved candidate. What/why: a SHA hidden in chat cannot
govern release work. How: write the evidence file, update TestFlight packet and
status docs, and define when work returns to TF-005.

**Procedure:**

1. Record full SHA, version, build, bundle, team, branch, scope, dependency
   evidence, and approvers.
2. Update `AppStore/testflight_metadata.md` build/SHA.
3. Update canonical backlog status.
4. State invalidation rule: any binary/source/content change requires new SHA;
   any replacement upload after successful processing requires a new build.
5. Have QA/release owner acknowledge the tuple before TF-006.

**Done when:** All downstream docs identify the same immutable tuple and owners
acknowledge change control.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-005-release-candidate.md`.

**Stop/escalate:** Mismatched SHA/build anywhere leaves TF-005 incomplete.
