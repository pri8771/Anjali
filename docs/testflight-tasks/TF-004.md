# TF-004 — Finalize the TestFlight Metadata and Review Packet

**Status:** ready for drafting; blocked on final TF-003 values  
**Owner:** product/release owner with content, privacy, and QA review  
**Depends on:** TF-003 final public/contact values; TF-005 supplies build/SHA  
**Blocks:** TF-009 and TF-011 Beta App Review  
**Canonical packet:** `AppStore/testflight_metadata.md`
**Prepared input:** source-backed copy audit at
`quality/evidence/2026-07-29-tf-003-tf-004-metadata-preflight.md`

## Task description

**Summary:** Produce truthful, copy-ready TestFlight information for Apple and
testers.

**Expected change:** As an Apple reviewer or beta tester, I want concise instructions
that accurately describe the build, tell me how to exercise it, and provide a
working feedback path.

**What and why:** External TestFlight uses beta-specific information that the
old storefront checklist omitted. Incorrect audio, login, privacy, or test-path
claims can cause review failure and tester confusion.

**How:** Start from the canonical packet, replace values only from approved
evidence, validate against the exact build, obtain named reviews, enter the
identical text in App Store Connect, and prove synchronization.

## Subtasks

### TF-004.1 — Bind the packet to product scope and build identity

**Description:** Summary: establish which product/build the copy describes.
Expected change: as a reviewer, I should not receive generic instructions detached
from the uploaded binary. What/why: build number/SHA placeholders must not be
guessed. How: confirm v1 scope now, then insert exact TF-005 build/SHA only after
candidate freeze.

**Procedure:**

1. Confirm scope: iOS 17+, iPhone/iPad, offline/accountless, text-only, optional
   local reminders, no IAP/analytics/network.
2. Review current feature contracts and release status.
3. Keep `[BUILD_NUMBER]` and `[FULL_GIT_SHA]` until TF-005 evidence exists.
4. After TF-005, copy exact values and independently compare with Xcode settings.
5. Record packet version/approval date.

**Done when:** Packet scope matches repository behavior and build/SHA match the
candidate.

**Evidence:** Scope checklist and TF-005 evidence link.

**Stop/escalate:** Any copy requiring an unimplemented feature is removed, not
implemented ad hoc.

### TF-004.2 — Finalize Beta App Description

**Description:** Summary: write the tester-facing beta summary. Expected change: as
a prospective tester, I can decide what the beta does before installing.
What/why: it must describe shipping functionality without marketing
overstatement. How: retain the approved concise description, verify every claim
against source/evidence, and explicitly state text-only audio behavior.

**Procedure:**

1. Verify each sentence in the template against `docs/FEATURES.md` and the
   candidate.
2. Keep offline, accountless, no tracking/purchases/network claims only if still
   true.
3. State that Listen is hidden without an exact approved human recording and
   that no provisional audio ships.
4. Avoid “personalized,” “recommendation,” medical, guaranteed-outcome, or
   culturally universal claims.
5. Obtain product/content owner approval.

**Done when:** Every description claim is evidenced and approved.

**Evidence:** Approver/date and claim-to-source checklist.

**Stop/escalate:** Privacy or content disagreement blocks approval.

### TF-004.4 — Finalize sign-in state and Review Notes

**Description:** Summary: tell Apple exactly how to enter and exercise the app.
Expected change: as an Apple reviewer, I can reach the primary path without asking
for credentials. What/why: Anjali has no account; incorrectly enabling sign-in
or omitting local-notification/text-only details wastes review time. How: set
Sign-in Required to No and verify the prepared notes against the build.

**Procedure:**

1. Confirm no onboarding step requires account credentials.
2. Set Sign-in Required to No; demo account Not Applicable.
3. Retain the explicit path: launch → onboarding → Today → Read silently →
   Begin silent prayer → Complete → Done.
4. Explain local-only notifications and denial behavior.
5. Explain no audio in this beta and the fallback.
6. Include only implemented deep links:
   `anjali://moment/anxiety` and `anjali://moment/beforeWork`.
7. Obtain engineering/privacy review.

**Done when:** A reviewer can exercise the app from notes alone, with no false
credential, network, or audio claim.

**Evidence:** Engineering/privacy approver/date.

**Stop/escalate:** If the supplied path fails on the candidate, fix/retest the
binary before changing notes to hide the issue.

### TF-004.5 — Finalize build-specific What to Test

**Description:** Summary: give testers a bounded, reproducible checklist. Expected change:
as a beta tester, I know the highest-value paths and what evidence to
include in a report. What/why: generic “test the app” requests produce poor
coverage. How: use the template's eight checks, insert exact build, and align
them with TF-007/TF-010 evidence.

**Procedure:**

1. Insert TF-005 build number.
2. Verify each listed flow exists on the processed candidate.
3. Keep fresh install, core self-led loop, truthful Listen omission,
   Moment/Intention/Deity browse, save/relaunch, reminders, deep links,
   airplane mode, dark mode, large text, and VoiceOver.
4. Ask reporters for device, OS, build, steps, expected/actual, and safe media.
5. Include exact prayer/field request for cultural feedback.
6. QA owner approves feasibility and priority.

**Done when:** What to Test is build-specific, executable, and approved by QA.

**Evidence:** QA approver/date and linked matrix coverage.

**Stop/escalate:** Remove no required check solely because it exposes a known
defect; link/fix the defect.

### TF-004.6 — Remove placeholders and obtain cross-functional approval

**Description:** Summary: finish the repository packet without inventing private
values. Expected change: as release operator, I can copy approved text without
editing or interpretation. What/why: leftover placeholders or unreviewed copy
create App Store Connect drift. How: run a placeholder search, classify private
fields, collect named approvals, and record packet SHA.

**Procedure:**

```bash
rg -n 'TBD|\\[[A-Z][A-Z0-9 _-]+\\]' AppStore/testflight_metadata.md
```

1. Replace every public placeholder from approved TF evidence.
2. For private contact values stored only in App Store Connect, replace the
   placeholder with an explicit note such as “stored in App Store Connect;
   verified by <role/date>,” not private data.
3. Obtain product, content, privacy, QA, and release approvals.
4. Record the packet Git SHA.

**Done when:** Search returns no unexplained placeholder and all named approvals
are recorded.

**Evidence:** Approval table and packet SHA.

**Stop/escalate:** Missing approval keeps TF-004 `verification_pending`.

### TF-004.7 — Enter and verify the App Store Connect copy

**Description:** Summary: synchronize Apple's Test Information with the repo.
Expected change: as a tester/reviewer, I see the same approved copy maintained by the
team. What/why: App Store Connect is a copy and can drift through manual entry.
How: an authorized operator copies each field exactly, saves, rereads the saved
values, and a second person compares them with the packet.

**Procedure:**

1. Open App Store Connect → app → TestFlight → Test Information.
2. Copy Beta App Description, Feedback Email, Review Contact, sign-in state,
   and Review Notes.
3. Add build/group What to Test when the build is available.
4. Save every section and reopen it.
5. Second verifier compares field by field to the repository packet SHA.
6. Record discrepancies and correct the authoritative repo first if content
   truly needs to change.

**Done when:** Saved App Store Connect values exactly match the approved packet.

**Evidence:** Redacted field comparison, operator/verifier/date, packet SHA.

**Stop/escalate:** Never fix drift only in App Store Connect; reconcile the
repository source first.
