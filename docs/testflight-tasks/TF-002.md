# TF-002 — Establish Apple Account, App ID, and App Record

**Status:** blocked  
**Owner:** Apple Developer Account Holder/Admin; App Manager for permitted
App Store Connect steps  
**Depends on:** authorized account access  
**Blocks:** TF-005, signing, upload, and all TestFlight distribution  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-002-apple-identity.md`
**Prepared input:** repository-only identity/capability preflight at
`quality/evidence/2026-07-29-tf-002-apple-identity-preflight.md`

## Task description

**Summary:** Establish the authorized and internally consistent Apple identity
for Anjali before any build is signed or uploaded.

**Expected change:** As a release owner, I want the bundle, team, app record, rights,
and regions to be confirmed once so that the correct product is signed and an
immutable App Store Connect record is not created with guessed values.

**What and why:** The repository contains team `796XH483R4`, bundle ID
`app.anjali.Anjali`, and name `Anjali`, but it cannot prove account ownership,
agreements, App ID, record existence, name availability, or rights. Apple uses
these values to associate uploads and restricts later changes.

**How:** An authorized human performs account mutations. A model may inspect
the repository, prepare exact field values, guide the operator, and record
redacted evidence, but must not claim an unseen account state.

## Subtasks

### TF-002.1 — Confirm membership, agreements, and roles

**Description:** Summary: prove the account can legally and operationally
distribute apps. Expected change: as the release team, we need accepted agreements
and appropriately privileged users so upload work does not fail late. What/why:
only authorized roles can create records/upload, and the Account Holder must
accept current agreements. How: the Account Holder checks membership and
Agreements, Tax, and Banking/Business areas as applicable, then confirms each
operator's role.

**Procedure:**

1. Sign into the intended Apple Developer/App Store Connect organization.
2. Confirm membership is active through the planned beta period.
3. Account Holder accepts every agreement blocking app creation/distribution.
4. Record the Account Holder/Admin/App Manager/Developer responsible for each
   later account action.
5. Do not record credentials or personal contact details in Git.

**Done when:** Membership is active, no blocking agreement remains, and each
distribution action has an authorized owner.

**Evidence:** Organization name, non-secret team ID, verification date, role
mapping, and redacted restricted-evidence reference.

**Stop/escalate:** Stop on expired membership, unsigned agreement, or missing
role; only the Account Holder/Admin can resolve it.

### TF-002.2 — Confirm team and explicit App ID

**Description:** Summary: match the repository bundle identity to an Apple
identifier. Expected change: as engineering, I need signing to use the intended
organization and exact bundle ID. What/why: a mismatch can create a different
app or make the upload unassociable. How: compare Xcode settings with the
developer portal and register the explicit ID only after ownership is confirmed.

**Procedure:**

1. Read Debug and Release app-target values in
   `Anjali/Anjali.xcodeproj/project.pbxproj`.
2. Confirm both use team `796XH483R4` and bundle `app.anjali.Anjali`.
3. In Certificates, Identifiers & Profiles, search for that exact explicit App
   ID.
4. If absent, Account Holder/Admin registers it; do not silently choose a
   similar identifier.
5. Record the App ID description and identifier without credentials.

**Done when:** Apple has an explicit App ID exactly matching the repository,
owned by the intended team.

**Evidence:** Team ID, bundle ID, portal verification date, operator.

**Stop/escalate:** Stop if another team owns the ID or product ownership is
uncertain. Do not rename the bundle as a workaround.

### TF-002.3 — Audit capabilities and signing surface

**Description:** Summary: keep Apple capabilities aligned with the local-only
product. Expected change: as a privacy-conscious user, I want the distributed app to
request only capabilities it actually uses. What/why: unexpected push, cloud,
associated-domain, or other entitlements can contradict architecture/privacy.
How: compare portal capabilities, Xcode Signing & Capabilities, entitlements
files, and the product boundary.

**Procedure:**

1. Inspect the app target's Signing & Capabilities and any `.entitlements`
   files.
2. Compare with the App ID capability list.
3. Confirm local notifications do not cause Push Notifications to be enabled.
4. Confirm no iCloud, Associated Domains, App Groups, Sign in with Apple,
   HealthKit, payments, or other unimplemented capability is present.
5. Document every enabled capability and its code owner.

**Done when:** Only capabilities required by the shipping implementation remain
enabled and repository/portal states agree.

**Evidence:** Redacted capability matrix and reviewer/date.

**Stop/escalate:** Any unexpected capability requires engineering/privacy
review before removal or acceptance.

### TF-002.4 — Create or verify the App Store Connect app record

**Description:** Summary: create the immutable record used by uploads. Expected change:
as a release operator, I need one correct App Store Connect destination
for version 1.0. What/why: name, bundle ID, SKU, language, and access influence
identity and later workflows. How: first search for an existing record; create
one only when duplication and field choices are resolved.

**Procedure:**

1. Search My Apps for existing records using the bundle ID.
2. If one exists, verify ownership and do not create a duplicate.
3. If absent, use Add New App with:
   - platform: iOS;
   - approved name;
   - approved primary language;
   - exact bundle ID;
   - non-sensitive stable SKU;
   - explicit user access.
4. Record the generated App Store Connect app Apple ID.
5. Verify the record is visible to the later upload operator.

**Done when:** Exactly one correct app record exists and authorized release
users can access it.

**Evidence:** Non-secret field table, app Apple ID, creator/date.

**Stop/escalate:** Stop before creation if name, bundle, SKU, or access is
unapproved; SKU/bundle choices are not disposable.

### TF-002.5 — Decide name and content rights

**Description:** Summary: resolve product identity and legal authority. Expected change:
as a tester, I should receive an app whose name and content are authorized
and not misleading. What/why: another accented `ANJĀLI` listing exists, and
religious text still requires an honest rights declaration. How: product/legal
owners review name confusion/trademark risk and document the basis for using
the bundled content.

**Procedure:**

1. Search App Store Connect and public storefront for confusingly similar names.
2. Present findings to product/legal owner; do not declare trademark clearance
   from search alone.
3. Record the approved final display/store name.
4. Inventory whether bundled text is public-domain traditional material,
   licensed translation, or otherwise owned/authorized.
5. Account owner answers Content Rights fields based on that documented basis.

**Done when:** Authorized owners approve the name and content-rights answer.

**Evidence:** Decision owner/date, final name, rights summary, restricted legal
reference where needed.

**Stop/escalate:** Legal uncertainty remains a human/legal blocker.

### TF-002.6 — Decide initial regions and compliance posture

**Description:** Summary: choose where the beta/store record may be distributed.
Expected change: as the account owner, I want to avoid enabling regions whose
compliance requirements have not been evaluated. What/why: Apple presents
region-specific compliance fields, including religious-information permit
fields for China mainland. How: account/legal owners choose initial regions and
explicitly exclude unresolved regions.

**Procedure:**

1. List intended beta and eventual storefront regions.
2. Review App Store Connect compliance prompts for each.
3. Do not enable China mainland until legal/account owner documents whether a
   permit applies and supplies it if required.
4. Record any other country-specific business/compliance requirement.
5. Save an approved initial-region list and owner/date.

**Done when:** Initial regions are explicit and every enabled region has an
owner-approved compliance answer.

**Evidence:** Region decision matrix; no private permit document in Git.

**Stop/escalate:** Default unresolved regions to excluded; do not guess.
