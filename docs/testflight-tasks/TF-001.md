# TF-001 — Complete Named Human Prayer-Content Sign-Off

**Status:** blocked  
**Owner:** product/content owner and named cultural/theological reviewer  
**Depends on:** reviewer appointment  
**Blocks:** TF-005 and every external distribution build  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-001-content-signoff.md`
**Prepared input:** `Content/tf-001-review-packet.md`; current preflight is
`quality/evidence/2026-07-29-tf-001-review-preflight.md`

## Task description

**Summary:** Obtain a real, named human review of every shipping prayer and bind
that approval to an exact repository commit.

**Expected change:** As a Hindu practitioner, I want every prayer, transliteration,
meaning, attribution, and contextual classification to have been checked by a
qualified human so that I can trust the app to present sacred material
respectfully and accurately.

**What and why:** The repository contains 22 structurally valid prayer records,
but none has named reviewer/date provenance. Code validation cannot establish
theological or cultural correctness. This task keeps the existing hard release
gate and makes approval auditable.

**How:** A model prepares the review packet, applies only decisions explicitly
made by the reviewer, runs validation/export checks, and records evidence. A
model must never act as the reviewer, invent an identity/date, or bulk-fill
approval fields.

## Required inputs

- `Anjali/Anjali/Resources/prayers.json`
- `Content/prayer_catalog_template.csv`
- `Content/content_review_checklist.md`
- `CONTENT_GUIDELINES.md`
- `Scripts/validate_prayers.py`
- `Scripts/export_catalog.py`

## Subtasks

### TF-001.1 — Appoint and record the reviewer

**Description:** Summary: identify the real person authorized to approve the
content. Expected change: as the content owner, I need one accountable reviewer
identity so every approval can be traced. What/why: generic values such as
“reviewer,” an AI name, or an organization do not prove human review. How: the
product owner selects the reviewer, confirms their competence and scope, agrees
on the exact display name to store, and records whether one reviewer covers all
22 records or multiple reviewers will be used.

**Procedure:**

1. Product owner supplies the person's real approved display name.
2. Confirm the reviewer agrees to inspect Sanskrit/Devanagari,
   transliteration, meaning, source, classifications, and tone.
3. If multiple reviewers are needed, map prayer IDs to reviewer names.
4. Record the appointment in the draft evidence file without private contact
   details.

**Done when:** Every prayer has an assigned real reviewer and the reviewer has
accepted the stated review scope.

**Evidence:** Reviewer display name(s), appointment date, scope, and prayer-ID
mapping.

**Stop/escalate:** Stop if no qualified human accepts the work. Do not substitute
model review.

### TF-001.2 — Freeze and export the review baseline

**Description:** Summary: create a stable review input tied to Git. Expected change:
as a reviewer, I want the text I approve to be immutable and identifiable so
later edits cannot inherit my approval. What/why: reviewing an uncommitted or
changing catalog makes provenance meaningless. How: record the starting SHA,
validate structure, export the catalog, and give the reviewer the JSON/CSV plus
the checklist.

**Procedure:**

1. Record `git rev-parse HEAD` and `git status --short`.
2. Confirm unrelated working-tree changes will not be lost or folded into
   content review.
3. Run `python3 Scripts/validate_prayers.py`; stop on any structural error.
4. Run `python3 Scripts/export_catalog.py`.
5. Record SHA-256 for `prayers.json` and the exported catalog.
6. Prepare a 22-row review packet using the existing checklist; do not modify
   sacred text during packet generation.

**Done when:** The reviewer has a 22-record packet, checklist, baseline SHA, and
file hashes.

**Evidence:** Baseline SHA, hashes, validator output, record count, packet
location.

**Stop/escalate:** Stop if structural validation fails or record count is not
22; resolve that as a separate content defect before human approval.

### TF-001.3 — Review every prayer field

**Description:** Summary: perform the actual human judgment. Expected change: as a
practitioner, I need each displayed field—not merely the title—to be trustworthy.
What/why: a correct mantra can still be harmed by bad transliteration, meaning,
source, deity, moment, or framing. How: the human reviewer works record by
record and marks Approved, Correction Required, or Rejected with notes.

**Procedure:**

1. For each prayer ID, inspect:
   - Devanagari/Sanskrit character by character;
   - IAST transliteration;
   - plain-English meaning;
   - `sourceTitle` and `provenance.sourceReference`;
   - deity, moments, intentions, and time contexts;
   - duration and respectful tone.
2. Record one explicit disposition per record.
3. Quote only the minimum affected field in correction notes.
4. Do not approve a record with an unresolved uncertainty.

**Done when:** All 22 prayer IDs have an explicit human disposition and no row
is silently skipped.

**Evidence:** Signed review matrix with 22 rows and correction/rejection notes.

**Stop/escalate:** Any unresolved or disputed sacred-text issue leaves the task
blocked.

### TF-001.4 — Apply approved corrections and review flags

**Description:** Summary: translate human decisions into canonical repository
data. Expected change: as a release owner, I need the app bundle to contain exactly
what the reviewer approved. What/why: correcting only a CSV or note would leave
the runtime JSON stale. How: edit `prayers.json` first, making only reviewer-
authorized changes; approved records use `isReviewed: true` and
`needsReview: false`, while unresolved records use the inverse.

**Procedure:**

1. For each Correction Required row, apply the exact reviewer-approved value to
   canonical JSON.
2. Show the reviewer the resulting changed field for confirmation.
3. Set approved records to `isReviewed: true`, `needsReview: false`.
4. Set unresolved/rejected records to `isReviewed: false`,
   `needsReview: true`; do not delete them unless product owner approves scope
   removal.
5. Leave all `audioAssetName` values null.
6. Review `git diff -- Anjali/Anjali/Resources/prayers.json` for unrelated edits.

**Done when:** Canonical JSON exactly reflects the review matrix and every
change has reviewer authorization.

**Evidence:** Diff summary and correction-to-prayer-ID mapping.

**Stop/escalate:** Stop if a requested correction is ambiguous, changes product
scope, or would require generating sacred text.

### TF-001.5 — Record named provenance

**Description:** Summary: attach real approval identity/date to approved
records. Expected change: as an auditor, I need to know who approved each prayer and
when. What/why: imported `isReviewed` flags alone are not release evidence. How:
after final human approval, set `provenance.reviewer` and
`provenance.reviewedOn` per approved record using the agreed name and actual ISO
date.

**Procedure:**

1. Confirm final approval again after corrections.
2. Set `provenance.reviewer` to the exact appointed display name.
3. Set `provenance.reviewedOn` to the real `YYYY-MM-DD` approval date.
4. Do not apply provenance to unresolved/rejected records.
5. Review the provenance-only diff against the signed review matrix.

**Done when:** Each approved record has accurate reviewer/date provenance and
no unresolved record appears signed.

**Evidence:** Prayer-ID, reviewer, and date table.

**Stop/escalate:** Never use a future date, inferred identity, placeholder, or
batch value not confirmed by the reviewer.

### TF-001.6 — Validate, export, and prove repeatability

**Description:** Summary: prove the approved data is structurally valid,
release-signed, text-only, and reproducibly exported. Expected change: as engineering,
I need deterministic gates so reviewed content reaches the app without format
or audio regressions. What/why: human approval does not catch JSON/schema drift.
How: run both validators, assert reviewed flags and audio exclusions, export
twice, and compare hashes.

**Procedure:**

```bash
python3 Scripts/validate_prayers.py
python3 Scripts/validate_prayers.py --require-signoff
rg -n '"isReviewed": false|"needsReview": true' \
  Anjali/Anjali/Resources/prayers.json
rg -n '"audioAssetName": "[^"]+"' \
  Anjali/Anjali/Resources/prayers.json
python3 Scripts/export_catalog.py
shasum -a 256 Content/prayer_catalog_seed.csv
python3 Scripts/export_catalog.py
shasum -a 256 Content/prayer_catalog_seed.csv
```

Both `rg` commands must return no matches; both catalog hashes must match.

**Done when:** Validators exit zero, `rg` finds no disallowed record/audio
state, and repeated export is byte-stable.

**Evidence:** Exact commands, exit statuses, validator counts, and hashes.

**Stop/escalate:** Fix the underlying content/export problem; never weaken a
validator to get green.

### TF-001.7 — Commit and obtain final reviewer sign-off

**Description:** Summary: bind approval to immutable Git evidence. Expected change:
as a future maintainer, I need to prove which content the human approved.
What/why: an unsigned working-tree review can be invalidated by later edits.
How: commit reviewed JSON/catalog, record the content SHA, rerun export from a
clean checkout, and have the reviewer sign the evidence referencing that SHA.

**Procedure:**

1. Commit only approved content/catalog changes with an intentional message.
2. Record the full content commit SHA.
3. From a clean checkout of that SHA, rerun both validators and exporter.
4. Require no new `Content/` diff.
5. Complete the evidence file with reviewer, date, SHA, 22/22 result,
   corrections, commands, and hashes.
6. Obtain the reviewer's explicit final approval of that SHA.
7. Commit the evidence file separately if necessary.

**Done when:** A named reviewer has approved the exact content SHA and the
release sign-off gate passes 22/22 at that SHA.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-001-content-signoff.md`.

**Stop/escalate:** Any content change after the approved SHA invalidates this
task for the new candidate and requires reviewer disposition.
