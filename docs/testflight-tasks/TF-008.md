# TF-008 — Create and Inspect a Signed Distribution Archive

**Status:** blocked  
**Owner:** authorized signing/release owner  
**Depends on:** TF-002, TF-005, TF-006, TF-007  
**Blocks:** TF-009  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-008-signed-archive.md`

## Task description

**Summary:** Produce an App Store-signed archive from the exact candidate,
validate it in Organizer, and inspect its signed identity/contents.

**Expected change:** As the upload operator, I want a validated archive whose signing,
entitlements, privacy files, and bundled content match the approved product.

**What and why:** An unsigned engineering archive proves construction only.
TestFlight requires authorized App Store distribution signing and Apple
validation.

**How:** Use an authorized Xcode environment, reconcile signing/capabilities,
archive exact SHA, validate in Organizer, inspect signed bundle/entitlements,
confirm export-compliance declaration, and record redacted evidence.

## Subtasks

### TF-008.1 — Prepare the authorized signing environment

**Description:** Summary: ensure toolchain and account access can create the
correct archive. Expected change: as release owner, I avoid signing on an unknown Mac
or wrong team. What/why: signing credentials are sensitive and environment
identity affects output. How: authorized human verifies Xcode/SDK, Apple account,
candidate checkout, and credential access without exporting secrets.

**Procedure:**

1. Check out exact TF-005 SHA; require clean tree.
2. Record macOS, Xcode, SDK, and TF-006/TF-007 evidence links.
3. Confirm Xcode account belongs to team `796XH483R4`.
4. Confirm membership/certificates/profiles are valid or automatic signing can
   manage them.
5. Restrict archive access to authorized operator.

**Done when:** Clean candidate and approved signing team are available in a
supported Xcode 26+/iOS 26 SDK environment.

**Evidence:** Environment, SHA, operator/date, non-secret credential status.

**Stop/escalate:** Do not copy private keys/profiles into repo or switch teams
to bypass access.

### TF-008.2 — Reconcile signing identity, capabilities, and entitlements

**Description:** Summary: make source, portal, and signing settings agree. Expected change:
as a privacy-conscious user, the signed app has only expected
entitlements. What/why: portal or profile drift can add/remove capabilities.
How: compare TF-002 matrix, Xcode Signing & Capabilities, resolved build
settings, entitlements, and provisioning state.

**Procedure:**

1. Confirm automatic/manual signing decision from TF-002.
2. Resolve Release settings for team/bundle/version/build.
3. Inspect every app entitlement/capability.
4. Confirm no Push Notifications, iCloud, App Groups, Associated Domains, or
   other unimplemented entitlement.
5. Resolve signing warnings before archive.

**Done when:** All identity/capability surfaces agree with TF-002/TF-005.

**Evidence:** Redacted reconciliation matrix.

**Stop/escalate:** Unexpected entitlement requires engineering/privacy owner.

### TF-008.3 — Create the signed App Store archive

**Description:** Summary: archive exact source with distribution signing. Expected change:
as uploader, I receive a reproducible candidate artifact. What/why:
archive creation can reveal device-only signing/resource failures. How: use
Anjali scheme, Release, generic/Any iOS Device destination, and signing enabled.

**Procedure:**

1. In Xcode, select Anjali scheme and Any iOS Device/generic iOS destination.
2. Confirm version/build before Product → Archive.
3. Archive with signing enabled; do not pass
   `CODE_SIGNING_ALLOWED=NO`.
4. Save archive creation log and Organizer timestamp.
5. Verify Organizer shows expected name, version/build, team, bundle, and source
   commit when available.

**Done when:** Signed archive completes and Organizer identity matches TF-005.

**Evidence:** Archive identity table/log reference.

**Stop/escalate:** Any identity mismatch invalidates the archive; do not upload.

### TF-008.4 — Run Organizer Validate App

**Description:** Summary: ask Apple tooling to validate the distribution
artifact before upload. Expected change: as release team, we catch signing/bundle/
metadata errors locally. What/why: archive success is not validation success.
How: select Validate App with intended App Store Connect destination/options,
record every warning/error, and resolve rather than dismiss.

**Procedure:**

1. In Organizer, select archive → Validate App.
2. Choose correct organization/app record.
3. Preserve validation result and timestamp.
4. Classify each warning/error with owner and disposition.
5. If source/build changes, discard archive and return to TF-005.
6. Revalidate after non-source account/signing correction.

**Done when:** Validation completes with no error and every warning is accepted
by the responsible owner.

**Evidence:** Redacted validation report and dispositions.

**Stop/escalate:** Never mark done with an unresolved validation error.

### TF-008.5 — Inspect signed entitlements and bundle

**Description:** Summary: verify the actual signed payload. Expected change: as
privacy/content owners, we know signing/export did not change identity or
contents. What/why: signed entitlements and archive files are authoritative.
How: locate `.app`, use read-only codesign/plist/file inspection, and compare to
TF-006.

**Procedure:**

```bash
codesign -d --entitlements :- "<SIGNED_ARCHIVE_APP_PATH>"
plutil -p "<SIGNED_ARCHIVE_APP_PATH>/Info.plist"
find "<SIGNED_ARCHIVE_APP_PATH>" -type f | sort
```

1. Confirm application identifier/team/bundle and expected entitlements.
2. Confirm version/build, minimum OS, device families, export flag.
3. Confirm icon, privacy manifest, catalog.
4. Require zero provisional audio file extensions.
5. Inspect system-only dynamic dependencies.
6. Redact signing identity/profile details in committed evidence.

**Done when:** Signed payload matches candidate identity, capabilities, privacy,
and text-only content.

**Evidence:** Redacted inspection summary and counts.

**Stop/escalate:** Unexpected entitlement/file/dependency invalidates archive.

### TF-008.6 — Confirm export-compliance determination

**Description:** Summary: have the accountable owner confirm encryption answers.
Expected change: as the developer, we provide accurate legal/compliance information
to Apple. What/why: `ITSAppUsesNonExemptEncryption = NO` reduces prompts but
does not transfer responsibility to the plist. How: compare binary behavior/
dependencies with Apple's current questions and obtain Account Holder/release
owner decision.

**Procedure:**

1. Confirm no custom/non-exempt encryption was added.
2. Confirm current Info.plist value.
3. Review Apple's current export-compliance guidance.
4. Authorized owner records the determination and expected App Store Connect
   answer.
5. If uncertain, obtain legal/export counsel; do not guess.

**Done when:** Named accountable owner confirms the declaration is accurate for
this binary.

**Evidence:** Owner/date/determination and official guidance link.

**Stop/escalate:** Legal uncertainty blocks upload compliance completion.

### TF-008.7 — Finalize signed-archive evidence and handoff

**Description:** Summary: give TF-009 one validated artifact identity without
leaking credentials. Expected change: as uploader, I can confirm the exact archive I
am sending. What/why: Organizer may contain multiple similar archives. How:
record archive UUID/path or restricted locator, SHA, version/build, validation,
inspection, warning disposition, and authorized uploader.

**Procedure:**

1. Complete the TF-008 evidence file.
2. Identify archive by creation time, version/build, bundle, SHA, and restricted
   artifact locator/checksum where safe.
3. Link validation/entitlement/compliance evidence.
4. Name authorized TF-009 operator.
5. Update canonical backlog.
6. Do not commit signed archive, profile, certificate, or private key unless a
   separate secure artifact policy authorizes it.

**Done when:** TF-009 operator can unambiguously select the validated archive
and all acceptance criteria are evidenced.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-008-signed-archive.md`.

**Stop/escalate:** Ambiguous archive identity prevents handoff.
