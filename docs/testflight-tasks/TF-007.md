# TF-007 — Complete Manual Accessibility and Device QA

**Status:** blocked  
**Owner:** named human QA/release owner  
**Depends on:** TF-006, assigned supported devices  
**Blocks:** TF-008/external readiness  
**Evidence template:** `docs/templates/TESTFLIGHT_QA_EVIDENCE.md`

## Task description

**Summary:** Have humans exercise accessibility, layouts, notifications, and
real-device behavior that automated simulator tests cannot prove.

**Expected change:** As a user with varied devices or accessibility settings, I want
the primary prayer flow to remain understandable, reachable, and truthful.

**What and why:** VoiceOver usability, actual notification delivery, contrast,
iPad composition, and physical-device lifecycle behavior require observation.
A model can guide/record but cannot fabricate human perception or device
results.

**How:** Copy the evidence template, run a declared device/OS matrix, record
Pass/Fail/N/A per row, file reproducible defects, retest fixes, and obtain named
go/no-go.

## Subtasks

### TF-007.1 — Prepare devices, accounts, and evidence matrix

**Description:** Summary: establish a complete, traceable manual test setup.
Expected change: as QA, I know which supported environments were covered. What/why:
ad hoc testing creates invisible gaps. How: copy the template, inventory real
devices/OS versions, install exact candidate, and assign human testers.

**Procedure:**

1. Copy template to dated TF-007 evidence file.
2. Fill SHA, version/build, distribution method, tester, device, OS.
3. Include compact supported iPhone/oldest practical supported OS, current large
   iPhone, iPad full screen, and iPad narrow multitasking.
4. Plan light/dark and default/largest text rows.
5. Confirm tester can change accessibility/notification settings safely.

**Done when:** Every required row has an assigned device/tester and exact build.

**Evidence:** Completed identity/device matrix header.

**Stop/escalate:** Missing required real device/OS is recorded Blocked, not N/A.

### TF-007.2 — Execute VoiceOver coverage

**Description:** Summary: verify spoken semantics and navigation. Expected change: as
a VoiceOver user, I can understand and complete every primary flow without a
trap. What/why: labels in source do not prove runtime order/traits/usability.
How: a human enables VoiceOver and swipes/activates through all named surfaces.

**Procedure:**

1. Test onboarding, Today, player modes, completion, Moments, Me, saved
   prayers, privacy, banners, and error alerts.
2. Record labels, traits, values, hints, focus order, grouped content, and modal
   focus.
3. Verify mode picker and Done/Repeat/Save are distinct/reachable.
4. Confirm no decorative element creates noise and no control traps focus.
5. Capture safe screen recording/audio notes for failures.

**Done when:** All required surfaces pass or defects are resolved/retested.

**Evidence:** Row results and defect links.

**Stop/escalate:** Unusable primary path is P0/P1 and blocks release.

### TF-007.3 — Test text scaling and Reduce Motion

**Description:** Summary: preserve usability at accessibility text sizes and
reduced motion. Expected change: as a large-text or motion-sensitive user, I can
finish a prayer without clipped actions or confusing animation. What/why:
automated reachability is not visual/usability approval. How: test representative
sizes including maximum and compare normal/Reduce Motion transitions.

**Procedure:**

1. Test default, large, and maximum accessibility text.
2. Inspect onboarding, Today card, player text/modes, completion actions,
   Moments filters/lists, Me settings, privacy/error messages.
3. Scroll where intended; fail critical text/action clipping or overlap.
4. Enable Reduce Motion and repeat primary path.
5. Confirm state changes remain understandable without excessive animation.

**Done when:** Critical content/actions remain readable/reachable and motion is
acceptable.

**Evidence:** Size/surface matrix, screenshots, defects/retests.

**Stop/escalate:** A workaround requiring the user to reduce text size fails.

### TF-007.4 — Verify contrast, color independence, and appearance

**Description:** Summary: inspect five visual time bands in light/dark modes.
Expected change: as a low-vision or color-vision user, I can read and understand the
interface. What/why: automated palette tests do not prove on-device contrast or
color-independent meaning. How: force/observe Dawn, Morning, Midday, Sunset,
Night; inspect foreground/accent/control states in both appearances.

**Procedure:**

1. Exercise all five time bands.
2. Inspect primary/secondary text, buttons, selection states, links, alerts,
   disabled states, and focus indicators.
3. Repeat light and dark mode.
4. Confirm meaning/status never depends only on color.
5. Use a contrast measurement tool for questionable pairs and record values.

**Done when:** Every palette/appearance row passes human inspection and required
contrast, with defects resolved.

**Evidence:** Ten-row palette matrix and measurement references.

**Stop/escalate:** Low contrast on a primary path blocks release.

### TF-007.5 — Verify iPad and adaptive layouts

**Description:** Summary: approve the phone-first UI on supported iPads. Expected change:
as an iPad user, I get a composed, reachable experience without extreme
stretching or overflow. What/why: device family 2 is enabled. How: run all core
screens full-screen, rotate through supported orientations, and test narrow
multitasking width.

**Procedure:**

1. Test iPad full screen in supported portrait/landscape orientations.
2. Test narrow supported multitasking width.
3. Inspect onboarding, tabs, Today card, full-screen player, completion,
   filters/lists, settings, privacy/alerts.
4. Check safe areas, keyboard if shown, modal sizing, line length, and action
   reachability.
5. Record cosmetic versus blocking findings.

**Done when:** All supported iPad states have no blocking layout defect.

**Evidence:** Device/orientation/width matrix and media.

**Stop/escalate:** If acceptable iPad UX cannot be achieved, product must
explicitly remove iPad support and reassess screenshots/scope; a model cannot.

### TF-007.6 — Verify local notifications on a real device

**Description:** Summary: prove permission and scheduling state matches actual
notification-center behavior. Expected change: as a user, reminders occur only after
opt-in and the app remains truthful after denial/revocation. What/why:
simulators/unit mocks cannot prove real delivery/tap routing. How: reset
permission as needed and execute grant/deny/revoke/schedule/deliver/tap cases.

**Procedure:**

1. Fresh install; confirm no permission request before explicit enable.
2. Enable reminder, grant permission, verify scheduled request and delivery.
3. Tap delivered notification and verify correct Moment route.
4. Repeat with denial; app remains usable and state/error is truthful.
5. Revoke in Settings, return to app, verify recovery guidance/state.
6. Toggle repeatedly and confirm no duplicates/stale enabled state.
7. Test foreground/background transitions around delivery.

**Done when:** Every notification row passes on a real device.

**Evidence:** Device/OS/times/results, redacted notification media.

**Stop/escalate:** False success, unsolicited permission, duplicate delivery, or
broken tap route is P1/blocking.

### TF-007.7 — Verify offline, deep-link, lifecycle, and persistence behavior

**Description:** Summary: test local-first promises across launches and external
entry points. Expected change: as a user without connectivity, my settings/saves and
primary prayer flow continue to work. What/why: real lifecycle/store behavior
can differ from simulator tests. How: use airplane mode, cold/warm deep links,
force quit, backgrounding, save/delete/settings, and no-audio flow.

**Procedure:**

1. Airplane-mode cold launch through onboarding and prayer completion.
2. Save a prayer, force quit, relaunch, confirm it remains.
3. Delete it, relaunch, confirm deletion remains.
4. Change script/mode/reminder preferences and verify persistence.
5. Open `anjali://moment/anxiety` and `anjali://moment/beforeWork` cold/warm.
6. Background/foreground during player and settings changes.
7. Confirm Listen is absent for every prayer without an exact approved human
   recording; verify Chant and Silent explain that no app voice plays.
8. Record any controlled persistence-degraded behavior if safely reproducible.

**Done when:** All rows pass on required real devices or resolved defects are
retested.

**Evidence:** Results and defect links.

**Stop/escalate:** Crash, data loss, unexpected networking, or synthetic audio
is P0/P1.

### TF-007.8 — Triage, retest, and sign manual go/no-go

**Description:** Summary: close the manual matrix with accountable judgment.
Expected change: as release owner, I know no required human result is missing.
What/why: “tested” is meaningless if failures/Not Run rows are hidden. How:
classify defects P0–P3, resolve/retest blockers, review all rows, and obtain
named signatures.

**Procedure:**

1. Ensure each required row says Pass, Fail, or `N/A — reason`.
2. File every failure with build/device/OS/steps/expected/actual/evidence.
3. Resolve and retest all P0 and release-blocking P1.
4. Review remaining P2/P3 with product owner and document disposition.
5. QA, engineering, product/content, and release owners sign GO or NO-GO.
6. Update canonical backlog.

**Done when:** Complete matrix has no open P0/blocking P1 and named owners sign
GO.

**Evidence:** Dated copy of `TESTFLIGHT_QA_EVIDENCE.md`.

**Stop/escalate:** A required `Not run` row prevents GO.
