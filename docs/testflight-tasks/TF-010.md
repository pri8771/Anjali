# TF-010 — Run Internal TestFlight and Record a Go/No-Go

**Status:** blocked  
**Owner:** internal QA lead and authorized TestFlight operator  
**Depends on:** TF-009  
**Blocks:** TF-011  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-010-internal-testflight.md`

## Task description

**Summary:** Install Apple's processed build through an internal TestFlight
group, rerun critical real-device checks, and issue an external-review go/no-go.

**Expected change:** As an external tester, I want the build to have survived the
actual Apple distribution path and internal device testing before I receive it.

**What and why:** Local/signed-archive QA cannot prove that App Store Connect's
processed binary installs and behaves correctly. Apple also requires an
internal group before an external group.

**How:** Create a minimal authorized internal group, add the exact build and
instructions, install on real iPhone/iPad, execute critical matrix rows, inspect
Apple feedback/crashes, resolve defects, and obtain named go/no-go.

## Subtasks

### TF-010.1 — Create and secure the internal tester group

**Description:** Summary: establish the prerequisite internal group with only
authorized App Store Connect users. Expected change: as account owner, I control who
can access pre-release sacred content. What/why: internal testers are privileged
users, not a public mailing list. How: select existing authorized users, create
a clearly named group, and record its purpose/owners.

**Procedure:**

1. Choose a group name such as `Anjali 1.0 Internal QA`.
2. Add the smallest useful set of engineering, QA, product/content, and release
   users.
3. Confirm each user is authorized and assigned app access.
4. Do not add external community testers as internal users merely to bypass
   Beta App Review.
5. Record group owner and membership count, not personal emails in Git.

**Done when:** Internal group exists with authorized users and an accountable
owner.

**Evidence:** Group name, purpose, count, owner/date.

**Stop/escalate:** Role/access errors return to TF-002/account owner.

### TF-010.2 — Add the exact build and What to Test

**Description:** Summary: make TF-009 build available with approved instructions.
Expected change: as an internal tester, I know which build and paths to test. What/why:
adding the wrong processed build invalidates evidence. How: compare
identity, select it, paste TF-004 What to Test, and verify saved assignment.

**Procedure:**

1. Compare version/build with TF-009 evidence.
2. Add only that build to the internal group.
3. Paste build-specific What to Test from canonical packet.
4. Save and reopen group/build assignment.
5. Record testing expiration and availability state.

**Done when:** Correct build is available to the correct internal group with
matching instructions.

**Evidence:** Redacted group/build comparison.

**Stop/escalate:** Build mismatch or unavailable state blocks invitations.

### TF-010.3 — Install and verify binary identity on real devices

**Description:** Summary: prove TestFlight installation on iPhone and iPad.
Expected change: as a tester, I can download, install, launch, and identify the
distributed build. What/why: processed binaries can fail installation or differ
from local artifacts. How: install through TestFlight, not Xcode, on at least
one real iPhone and iPad and confirm displayed/system version.

**Procedure:**

1. Record device model, OS, prior install state, tester role.
2. Install from TestFlight on real iPhone and iPad.
3. Confirm installation and first launch.
4. Verify app's displayed version/build and device Settings metadata match
   TF-005/TF-009.
5. Record TestFlight build/expiration.

**Done when:** Exact processed build installs and launches on both form factors.

**Evidence:** Redacted device/install/identity table.

**Stop/escalate:** Installation/identity mismatch blocks all further testing.

### TF-010.4 — Execute core, offline, and persistence smoke paths

**Description:** Summary: rerun highest-risk functional paths on Apple's binary.
Expected change: as a user, I can complete, save, relaunch, and work offline.
What/why: internal TestFlight must validate distribution output, not rely on
TF-007 local results. How: copy the QA template and execute fresh install/core
loop/no-audio/browse/save/relaunch/airplane cases.

**Procedure:**

1. Fresh install and complete/skip onboarding.
2. Confirm Listen is absent without approved human audio; exercise Chant and
   Silent through explicit Begin → pause/resume → Complete → Done/Repeat/Save.
3. Browse by Moment, Intention, and Deity and open/save a prayer.
4. Force quit/relaunch; verify onboarding/settings/saves.
5. Delete and verify deletion after relaunch.
6. Repeat primary flow in airplane mode.
7. Record Pass/Fail per device.

**Done when:** Required core/offline/persistence rows pass on processed build.

**Evidence:** TF-010 QA matrix rows and defects.

**Stop/escalate:** Crash, data loss, privacy mismatch, or unexpected audio is
P0/P1.

### TF-010.5 — Execute notification, deep-link, and accessibility smoke

**Description:** Summary: verify distribution build integrations and accessible
primary path. Expected change: as a tester using reminders/accessibility, behavior
matches prior human QA. What/why: signing/processing should not alter these
surfaces, but the actual binary needs confirmation. How: perform focused real-
device cases from TF-007.

**Procedure:**

1. Grant/deny local notifications; schedule, deliver, tap, disable.
2. Test repeated toggles and Settings revocation.
3. Open both implemented deep links cold/warm.
4. Run primary path with VoiceOver and maximum text.
5. Check dark mode/Reduce Motion.
6. Inspect iPad full-screen and narrow width.

**Done when:** Focused integration/accessibility rows pass.

**Evidence:** Device-specific results/media/defects.

**Stop/escalate:** Any regression returns to candidate fix workflow.

### TF-010.6 — Review TestFlight crashes and feedback

**Description:** Summary: examine Apple's distribution diagnostics alongside
manual observations. Expected change: as release owner, I know the beta is not
silently crashing for internal users. What/why: Apple may expose crash/feedback
not seen in one session. How: inspect TestFlight build metrics/feedback after
internal use, correlate with devices, and file repository defects.

**Procedure:**

1. Open TestFlight build feedback/crash sections.
2. Record crash count/symbolication state and feedback count.
3. Review every item; link duplicates.
4. File canonical repo defect with severity and evidence.
5. Do not add analytics to measure internal behavior.

**Done when:** All available crash/feedback items are triaged.

**Evidence:** Aggregate/redacted queue summary and defect links.

**Stop/escalate:** Unexplained crash cluster blocks GO.

### TF-010.7 — Resolve findings and sign external-review go/no-go

**Description:** Summary: make an accountable decision about TF-011. Expected change:
as future external tester, I receive no known release-blocking internal defect.
What/why: completion requires more than an install. How: review every matrix
row/defect, require new candidate for binary fixes, and collect named approvals.

**Procedure:**

1. Ensure required rows are Pass or justified N/A; no Not Run.
2. Confirm no open P0/release-blocking P1.
3. Binary fix returns to TF-005 with new unique build and reruns TF-006 onward.
4. Metadata fix updates TF-004/reverification.
5. Engineering, QA, product/content, and release owners sign GO/NO-GO.
6. Record build expiration and update backlog.

**Done when:** Exact processed build has complete evidence and named GO for
external Beta App Review.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-010-internal-testflight.md`.

**Stop/escalate:** Any missing row/blocker keeps NO-GO.
