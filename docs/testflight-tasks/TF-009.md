# TF-009 — Upload, Process, and Clear Compliance

**Status:** blocked  
**Owner:** authorized Account Holder/Admin/App Manager/Developer  
**Depends on:** TF-004, TF-008  
**Blocks:** TF-010  
**Primary evidence:** `quality/evidence/YYYY-MM-DD-tf-009-upload-processing.md`

## Task description

**Summary:** Upload the validated signed archive and move the resulting Apple
build into a TestFlight-eligible, compliance-cleared state.

**Expected change:** As an internal tester, I want Apple's processed binary—not a
local look-alike—to be available for installation.

**What and why:** A successful local archive does not prove upload, server-side
processing, export compliance, or TestFlight eligibility. Apple status and
warnings must be recorded rather than inferred.

**How:** An authorized operator rechecks artifact/record identity, uploads the
TF-008 archive, monitors processing, resolves compliance and warnings, enters
approved Test Information, and publishes a build-status handoff.

## Subtasks

### TF-009.1 — Perform the pre-upload identity and authorization check

**Description:** Summary: ensure the operator is about to send the correct
archive to the correct app. Expected change: as release owner, I avoid an irreversible
successful upload under the wrong version/build/record. What/why: Apple uses
bundle/version/build to associate and uniquely identify builds. How: compare
TF-002, TF-005, TF-008, Organizer, and App Store Connect immediately before
upload.

**Procedure:**

1. Confirm operator role permits upload.
2. Open the exact TF-008 validated archive.
3. Compare team, bundle, app record, marketing version, build, and archive time
   to evidence.
4. Recheck App Store Connect does not already contain the build.
5. Confirm external testing is intended; do not mark upload
   TestFlight Internal Only.
6. Confirm no source/archive changed after TF-008.

**Done when:** Two-person comparison shows exact archive/record identity and
upload authorization.

**Evidence:** Preflight table, operator/verifier/date.

**Stop/escalate:** Any mismatch or duplicate build blocks upload.

### TF-009.2 — Upload the validated archive

**Description:** Summary: transmit the signed binary through Apple's supported
delivery flow. Expected change: as release team, we receive a traceable delivery
record. What/why: clicking Upload is consequential and must be tied to the
validated artifact. How: use Organizer/Transporter under the authorized account,
review options, upload once, and record delivery identifiers/output.

**Procedure:**

1. In Organizer choose Distribute App → App Store Connect → Upload.
2. Select approved distribution options; preserve automatic symbol/upload
   choices required by current Xcode policy.
3. Review summary for app/version/build/team.
4. Start upload once.
5. Save delivery/upload ID, timestamp, operator, and complete delivery log.
6. Do not retry while the first delivery state is unknown.

**Done when:** Apple reports delivery/upload completion, or a fully recorded
failure exists for diagnosis.

**Evidence:** Delivery ID/time/result/log reference.

**Stop/escalate:** On failure, diagnose exact Apple message before retry. If no
successful processing occurred Apple may allow reuse; verify current state,
never assume.

### TF-009.3 — Monitor server-side processing

**Description:** Summary: wait for Apple to ingest/analyze the build. Expected change:
as tester, I need a build visible in TestFlight, not merely uploaded.
What/why: processing is asynchronous and can fail later. How: monitor App Store
Connect/email until terminal or actionable state, recording status history.

**Procedure:**

1. Locate the build under the expected app/version.
2. Record initial processing status/time.
3. Recheck at reasonable intervals; do not upload duplicates to speed it up.
4. Capture every status transition and Apple email.
5. If processing fails, preserve exact error and map to owning task.
6. If still processing after 24 hours, contact Apple Developer Support with
   delivery ID.

**Done when:** Build exits processing into a known TestFlight/build status.

**Evidence:** Status/timestamp history and support case if needed.

**Stop/escalate:** Unknown/missing build or >24-hour processing remains blocked.

### TF-009.4 — Resolve export compliance

**Description:** Summary: clear Apple's encryption/compliance state accurately.
Expected change: as Apple and users, we receive truthful compliance declarations.
What/why: a build can show Missing Compliance even with the plist flag. How:
use TF-008 determination to answer current App Store Connect questions; never
invent legal conclusions.

**Procedure:**

1. Check build status for Missing Compliance.
2. Compare current questions to TF-008.6 evidence.
3. Authorized owner supplies exact answers and documentation if Apple requests
   it.
4. Save and verify the build no longer shows unresolved compliance.
5. Record questions/answers at a non-sensitive summary level.

**Done when:** Build has no unresolved export-compliance requirement.

**Evidence:** Owner/date, status before/after, determination reference.

**Stop/escalate:** Any answer inconsistent with binary/plist returns to
engineering/legal review.

### TF-009.5 — Triage processing warnings and verify build metadata

**Description:** Summary: confirm Apple's view of the binary is correct. Expected change:
as release owner, I want no hidden privacy, icon, platform, signing, or
device warning. What/why: some upload warnings do not block processing but can
block review/readiness. How: inspect build details, classify each warning, and
compare metadata to evidence.

**Procedure:**

1. Verify bundle, version/build, minimum OS, supported devices, app icon, and
   processing status.
2. Review signing, privacy-manifest, required-reason API, symbol, icon, and
   export warnings.
3. Assign every warning an owner and disposition.
4. Source/binary corrections return to TF-005 with a new build.
5. Account/metadata-only corrections are recorded and reverified.

**Done when:** Identity matches and no unresolved blocking/material warning
remains.

**Evidence:** Build-detail comparison and warning table.

**Stop/escalate:** Never dismiss a privacy/signing warning as cosmetic without
responsible-owner approval.

### TF-009.6 — Enter and verify Test Information

**Description:** Summary: attach the TF-004 approved beta packet to Apple's
processed build/app. Expected change: as reviewer/tester, I receive accurate
instructions and contact information. What/why: processed binary alone is
insufficient for external review and useful testing. How: copy approved fields,
add build-specific What to Test, save, and independently compare.

**Procedure:**

1. Verify TF-004 packet SHA/approval.
2. Enter Beta App Description, Feedback Email, Review Contact, sign-in state,
   and Review Notes.
3. Add exact build-specific What to Test where App Store Connect requests it.
4. Reopen saved fields.
5. Second verifier compares with canonical packet.
6. Correct authoritative repo first if copy genuinely changes.

**Done when:** App Store Connect Test Information exactly matches approved
repository packet.

**Evidence:** Redacted field comparison, operator/verifier/date.

**Stop/escalate:** Placeholder, drift, or invalid contact blocks handoff.

### TF-009.7 — Publish TestFlight-eligibility evidence

**Description:** Summary: create a definitive handoff to internal testing. Expected change:
as TF-010 owner, I know which Apple build is safe to add. What/why:
“upload succeeded” omits processing/compliance status. How: consolidate delivery,
status, metadata, warnings, and operator approval in one evidence record.

**Procedure:**

1. Record app Apple ID, bundle, version/build, TF-005 SHA, delivery ID/time.
2. Record final upload/build/compliance status.
3. Link warning dispositions and Test Information packet SHA.
4. Confirm build was not uploaded internal-only if TF-011 is planned.
5. Name TF-010 internal group/operator.
6. Update canonical backlog.

**Done when:** Exact build is eligible for internal testing with no unresolved
processing/compliance blocker.

**Evidence:** `quality/evidence/YYYY-MM-DD-tf-009-upload-processing.md`.

**Stop/escalate:** Any status uncertainty leaves TF-009 incomplete.
