## 00. Executive Summary
Anjali is a Hindu short-form **micro-prayer** iOS app — "a sacred pause, not a session." The user opens it, receives or chooses one prayer for the moment, practices briefly, and returns to the day. Chant is self-led aloud with no recording; Silent is inward reading or repetition with no sound. Listen is conditional on an exact approved human recording and is hidden in current normal builds, which contain no provisional audio. It is a daily ritual object, not a puja guide, meditation library, bhajan player, astrology app, or content feed. The product is a working SwiftUI app (iOS 17+) with 22 structurally valid bundled prayer records, a content pipeline, and automated tests. It is **not externally TestFlight-ready**: named cultural/theological sign-off is 0/22, and responsive UI, device, accessibility, distribution, and consumer gates remain.

## 01. Product
**MVP scope (as built):** optional two-screen first-run orientation with live script preview; three tabs (Today, Find, Me); a single contextual Today prayer card themed by five time bands (Dawn / Morning / Midday / Sunset / Night); a full-screen player that always shows the complete prayer text and meaning; self-led Chant and Silent modes with explicit controls and completion; conditional Listen shown only for an exact approved recording; completion ("May this action be steady." with Done / Repeat / Save); anytime discovery by Moment, Intention, or Deity inside Find; Me preferences (script, mode, ishta devata, situations to prioritize), editable opt-in local reminder times, and saved prayers; `anjali://` deep links; fully offline. A Moment is a situation in the user's day and is not clock-restricted; Intention represents the inner aim; Deity is a separate devotional filter. **Acceptance criteria:** the brief pause is clear and singular, every mode tells the truth about sound, content is respectfully and honestly sourced, and the core loop runs end-to-end. Detailed implementation and remaining work are in [DAILY_USE_PRODUCT_PLAN.md](DAILY_USE_PRODUCT_PLAN.md).

## 02. Design
Warm, reverent, minimal. Each of the five time bands has its own gradient, accent, and copy; the flame motif recurs in suggested progress, completion, and the app icon. No gamification, badges, or streak pressure. The player uses one stable layout, labels Prayer Text and Meaning, explains the selected mode, and keeps explicit controls visible. Discovery explains that Moments are available anytime and separates them from Intentions and Deities. Reduce Motion is honoured in code; human motion, contrast, VoiceOver, and responsive-layout review remain pending. A 1024×1024 RGB icon with no alpha is bundled; human small-size brand review also remains pending.

## 03. Frontend Technical
SwiftUI, iOS 17+, Swift 5.0 language mode. Core types: `Prayer` / `PrayerText` (immutable, Codable, from `Resources/prayers.json`); enums `TimeContext`, `Moment`, `Deity`, `Intention`, `PlayMode`, `ScriptPreference`, `RotationPolicy`; SwiftData `@Model`s `PrayerCompletion` and `FavoritePrayer`. The deterministic core (`TodayContextEngine`, `TimeBandResolver`, `PrayerDataLoader`) is pure and unit-tested, separated from the views. `AppCoordinator` owns navigation; `AppSettings` stores preferences and per-slot reminder times in UserDefaults; `PlayerController` drives explicit start/pause/completion state. `PrayerAudioAssetResolver` uses the approved-catalog policy for normal Debug, device, Release, and TestFlight builds, so a missing recording removes Listen instead of starting a pretend timed fallback. Navigation surfaces remain Today, Find, and Me. See [ARCHITECTURE.md](../ARCHITECTURE.md).

## 04. Backend Technical
**No backend, by design.** There is no networking layer in the MVP. All prayer content ships in the bundle; user state is on-device only (SwiftData + UserDefaults). Future, out-of-scope services could include optional iCloud sync of favourites/preferences or downloadable audio packs — none are built and any would be opt-in.

**Cloud-Pro direction (discussed 2026-08-14, not scoped, not scheduled).** A possible future opt-in cloud tier — pronunciation feedback on chanted prayers via a cloud speech model, or personalized practice curation — is a portfolio-wide direction, not an Anjali-specific plan yet. It does not change anything above: the free, no-account, no-tracking product stays exactly as shipped and disclosed unless and until a cloud tier is explicitly decided and privacy-relabeled per `DEC-002`'s standing rule that any future network or SDK work requires a documented decision and privacy reassessment. **Any cloud-generated or cloud-curated spiritual content specifically requires the same human cultural/religious sign-off already required for bundled content** (see `docs/RISKS.md` RISK-007 and the B6 precedent in Japa/Mala's `docs/BUGS.md`) — an LLM must not be the sole source of anything presented as prayer content. Portfolio-wide shared-infra direction: PostHog (analytics, multi-project) and Supabase (shared backend), namespaced per app.

## 05. Business
Trust-first spiritual product. v1 is free, no account, no ads, no tracking, no in-app purchases (confirmed by `privacy_policy.md` / `terms_of_service.md` and the absence of any StoreKit config). Any future monetization (premium recorded-audio packs, family features) must pass the north-star test: deepen *the pause*, never pull toward *the session*.

## 06. Marketing
Positioning: "A sacred pause, not a session — one short Hindu prayer for the moment you're in." Organic-only plan: temples, cultural centres, yoga communities, diaspora networks, and Product Hunt; **no paid advertising for MVP**. Marketing language deliberately avoids "feed", "for you", and "discover" to stay aligned with the no-recommendation principle. See [AppStore/marketing_plan.md](../AppStore/marketing_plan.md) (note: that file's Markdown formatting needs cleanup) and [AppStore/README.md](../AppStore/README.md) for listing copy.

## 07. User Acquisition
Beta with cultural advisors, diaspora users, students, and community contacts (see [AppStore/beta_testing_plan.md](../AppStore/beta_testing_plan.md)). Because nothing leaves the device, beta evidence comes from TestFlight install/crash information, explicit tester reports, interviews, and the monitored feedback email. There is no remote product analytics and no reliable completion-rate or retention measurement. Do **not** optimize time-in-app.

## 08. Execution
The current implementation passes 75/75 unit/integration tests and 4/4 current UI tests on each of large iPhone, compact iPhone, and iPad (12/12 total). The UI suite covers first use through explicit completion, largest accessibility text, saved-prayer relaunch persistence, and Om Namo Narayanaya without an unsupported Listen mode. Normal builds contain no provisional audio. Manual device, human accessibility, notification-delivery, and consumer verification remain pending. Audio acquisition and approval follow [AUDIO_LYRIC_ALIGNMENT_PLAN.md](AUDIO_LYRIC_ALIGNMENT_PLAN.md); daily-use implementation follows [DAILY_USE_PRODUCT_PLAN.md](DAILY_USE_PRODUCT_PLAN.md). ## 10. Legal / Compliance
Local-only data storage and opt-in local reminders are documented in [privacy_policy.md](../AppStore/privacy_policy.md). `PrivacyInfo.xcprivacy` is bundled and declares no tracking, no collected data, and UserDefaults reason `CA92.1`; App Store Connect must use matching answers. Religious content must be reviewed for respectful, accurate, non-sectarian presentation, with honest sourcing and **no fabricated Sanskrit** ([CONTENT_GUIDELINES.md](../CONTENT_GUIDELINES.md)); the named-reviewer release gate currently blocks 0/22 signed records. A public, verified-live privacy-policy URL is still required.
